 1. 프로젝트 한눈에
════════════════════════════════════════════════════════════════════════════

· 무엇을 하나
  - 네이버 뉴스를 키워드로 수집 → 유사한 뉴스를 한 묶음(그룹)으로 정리 →
    그룹 대표 1건만 LLM(생성형 AI)으로 분석 → "호재/악재/중립", 영향도 점수,
    관련 섹터·종목을 뽑아 그룹 전체에 전파 → 대시보드로 시각화.
  - KIS(한국투자증권) OpenAPI로 실시간 시세를, DART로 재무를 붙여 보여준다.

· 설계의 핵심 한 줄
  - "뉴스 건건이 분석하지 않는다." 유사 그룹화로 묶고 대표 1건만 LLM에 보낸다.
    LLM 호출이 곧 비용/한도이므로, 호출 수를 줄이는 것이 전체 설계의 중심축.

· 기술 제약(고정, 변경 불가)
  - JDK 8 / 순수 Servlet 3.0 + JSP + MariaDB + Tomcat WAR 구조.
  - Spring Boot, React, FastAPI 등 도입 금지. (레거시·학습 환경 기준)

 2. 사용한 도구·프로그램 — 무엇을, 왜, 장단점
════════════════════════════════════════════════════════════════════════════

[2-1] Java 8 (JDK 8)
  · 무엇   : 백엔드 구현 언어/런타임.
  · 왜     : 프로젝트 제약(고정). 사내/학습 환경이 JDK8 기준.
  · 장점   : 광범위한 라이브러리 호환, 안정성, Servlet/JSP와 자연스러운 결합.
  · 단점   : 최신 문법(var, record, switch식 등)·최신 라이브러리 상위버전 사용 불가.
             람다/스트림 정도까지만 활용 가능.

[2-2] Servlet 3.0 + JSP (순수 자바 웹)
  · 무엇   : HTTP 요청 처리(Servlet)와 화면 템플릿(JSP).
  · 왜     : 프레임워크 없이 가볍게. 제약상 Spring 금지.
  · 장점   : 의존성 최소, 컨테이너만 있으면 동작, 학습/디버깅 단순.
  · 단점   : 라우팅·DI·검증 등을 직접 구현해야 함(보일러플레이트 多).
             대규모로 가면 구조가 흩어지기 쉬움.

[2-3] Apache Tomcat 8.5 (WAR 배포)
  · 무엇   : 서블릿 컨테이너(웹서버).
  · 왜     : Servlet/JSP 표준 구현체, WAR 배포 단순.
  · 장점   : 가볍고 익숙함, 핫 배포(webapps에 WAR 복사) 가능.
  · 단점   : 형제 프로젝트와 같은 Tomcat을 공유 → 포트/컨텍스트 충돌 위험.
             → 컨텍스트를 '/newssignal2'로 분리해 회피.

[2-4] MariaDB 10.1 (utf8mb4)
  · 무엇   : 관계형 DB(뉴스/그룹/분석/매핑/설정 저장).
  · 왜     : MySQL 호환·무료, 한국어 저장(utf8mb4) 필요.
  · 장점   : SQL 친숙, 트랜잭션, 집계 쿼리로 대시보드 데이터 산출 용이.
  · 단점   : (이번에 겪음) 한글 멀티바이트에서 REGEXP가 불안정 → 데이터 정리 시
             LIKE/FIND_IN_SET 같은 정확한 함수로 우회.

[2-5] HikariCP 4.0.x (커넥션 풀)
  · 무엇   : DB 커넥션 풀.
  · 왜     : 요청마다 커넥션 새로 여는 비용 제거, 빠르고 안정적.
  · 장점   : 업계 표준 수준의 빠른 풀, 누수 감지.
  · 단점   : DB가 안 떠 있으면 풀 초기화(checkFailFast)에서 컨텍스트 시작 실패
             → 404. (그래서 start.ps1이 MariaDB를 먼저 띄우도록 구성)
  · 버전   : JDK8 상한 때문에 4.0.x 고정(상위는 JDK11+).

[2-6] mariadb-java-client 2.7.x (JDBC 드라이버)
  · 왜     : MariaDB 접속. JDK8 호환 상한이 2.7.x.

[2-7] Gson (JSON 직렬화/역직렬화)
  · 무엇   : 자바 객체 ↔ JSON.
  · 왜     : 외부 API(네이버/KIS/DART/LLM) 응답이 모두 JSON. 가볍고 단순.
  · 장점   : 의존성 작음, lenient 파싱.
  · 단점   : 스키마 강제는 약함 → LLM 응답이 배열/객체로 들쭉날쭉할 때
             직접 분기 파싱(parseBatchResults) 필요.

[2-8] Maven (빌드)
  · 왜     : WAR 패키징·의존성 관리 표준.
  · 장점   : 선언적 의존성, IDE 호환.
  · 단점   : 과거 Maven Central 차단 환경에서 빌드 검증이 어려웠음(인수인계 이슈).

[2-9] 네이버 뉴스 Search API
  · 무엇   : 키워드로 뉴스 검색(제목/요약/링크/언론사/발행일).
  · 왜     : 합법적·공식 뉴스 수집 경로(약관 안전). 서버사이드 호출(CORS·키 보호).
  · 장점   : 안정적, 일일 25,000회로 넉넉, 키워드 검색이 명확.
  · 단점   : 본문 전문은 안 줌(요약만) → 분석은 제목+요약 기반. 일일 한도 존재
             → QuotaGuard로 관리.

[2-10] KIS(한국투자증권) OpenAPI
  · 무엇   : 실시간 시세/일별 차트(거래량/거래대금/시총/현재가).
  · 왜     : 뉴스 옆에 "지금 이 종목이 어떻게 움직이나"를 붙이기 위해.
  · 장점   : 실시간·정확.
  · 단점   : (이번에 겪음) 토큰 발급 1분당 1회(EGW00133), 초당 호출 제한(EGW00201)이
             매우 빡빡. 게이트웨이가 토큰 발급까지 합산해 카운트.
             → 캐시 + throttle + 토큰 디스크 영속화로 대응.

[2-11] DART OpenAPI (금융감독원)
  · 무엇   : 기업 재무(매출/영업이익)·개황.
  · 왜     : 종목표에 펀더멘털 정보 보강.
  · 장점   : 공시 기반 신뢰 데이터.
  · 단점   : 종목코드→corp_code 변환 필요, 호출/매핑 비용.

[2-12] LLM(생성형 AI) — 최종: Groq 클라우드 / 대안: Gemini, Ollama
  · 무엇   : 뉴스 텍스트를 읽고 호재/악재·영향도·섹터·종목을 JSON으로 산출.
  · 왜     : 규칙(룰)만으로는 맥락 판단이 어려움(예: "캐즘 장기화"가 악재인지).
  · 현재   : Groq(클라우드, OpenAI 호환) + 모델 llama-3.3-70b-versatile.
  · 장점   : 무료 티어가 넉넉하고 매우 빠름(1건 ~2초), 한국어 분석 양호.
  · 단점   : Cloudflare 뒤에 있어 Java 기본 User-Agent를 차단(403) → UA 헤더로 해결.
             무료 RPM/TPM 한도는 있으니 배치+짧은 간격으로 준수.
  · (대안/중단 이력은 3장 참조)

[2-13] Git / GitHub
  · 왜     : 버전관리·백업·공유.
  · 장점   : 이력 추적, 협업.
  · 단점   : (주의) 비밀키가 든 start.ps1을 그대로 올리면 노출 → .gitignore +
             start.ps1.example 템플릿으로 분리. env/(수 GB 번들)도 제외.

[2-14] PowerShell 기동 스크립트(start.ps1)
  · 왜     : 환경변수(키)+MariaDB+Ollama 자동기동+빌드+배포+Tomcat을 한 번에.
  · 장점   : 원클릭 기동, 재부팅 후 404(=DB 미기동) 재발 방지.
  · 단점   : 키가 평문으로 들어가므로 커밋 금지 대상(=.gitignore).

 3. 사용하다 그만둔 것 — 무엇을, 왜 버렸나 (장단점 비교)
════════════════════════════════════════════════════════════════════════════

[3-1] Gemini 무료 티어 (분석 1차 선택 → 보조로 강등)
  · 썼던 이유 : 구글 생성형 AI, 한국어 양호, API 단순.
  · 장점      : 품질 좋음, 무료.
  · 버린/강등 이유: gemini-2.5-flash-lite 무료 RPD(Requests Per Day)가 "하루 20회"로
                    실측 확인됨. 배치(5~8그룹/호출)로 늘려도 하루 ~160그룹이 한계 →
                    매일 쌓이는 백로그를 못 따라감.
  · 현재      : provider 옵션으로 남겨둠(analyze.provider=gemini 로 전환 가능).
  · 교훈      : "무료 = 무제한"이 아니다. 모델별 RPD를 반드시 실측해야 한다.

[3-2] Ollama 로컬 LLM (무료·무제한 목적 → 속도 문제로 보류)
  · 썼던 이유 : 호출 한도 0, 비용 0, 데이터가 로컬에만 머무름(프라이버시).
  · 장점      : 무제한·무료·오프라인.
  · 버린/보류 이유: 이 PC는 GPU(Intel Arc)를 Ollama가 못 써서 100% CPU 추론.
                    품질 되는 모델(EXAONE 7.8B)은 1건에 ~72초 → 200건 ≈ 4시간.
                    실시간성이 떨어져 "버튼 누르면 몇 시간 spinning" 발생.
  · 현재      : provider 옵션으로 남김(GPU 머신이면 유효). start.ps1이 자동기동.

  · 모델 비교 (Ollama 안에서 검토한 것들)
    - qwen2.5:7b     : 빠르지만 한국어 작업에서 "중국어로 드리프트"(SK海星 등) → 부적합.
    - exaone3.5:2.4b : 매우 빠름(2건 15초)이나 복잡한 JSON 스키마를 못 따라가
                       빈 출력({})/영어 잡설 → 부적합.
    - exaone3.5:7.8b : LG 한국어 특화, 품질 양호(SK하이닉스 000660 정확)지만
                       CPU라 느림 → 품질은 OK, 속도가 문제.
  · 교훈      : 한국어 특화 모델(EXAONE)이 일반 모델(qwen)보다 한국어 안정적.
                작은 모델은 빠르지만 구조화 출력(JSON)을 못 지킬 수 있다.

[3-3] OpenAI (gpt-4o-mini) — 코드에 남아있으나 미사용(dummy_key)
  · 썼던 이유 : 범용 강력 모델, JSON 모드 지원.
  · 버린 이유 : 유료(과금) 부담 + 무료 대안(Groq) 확보. 키를 dummy로 둬 호출 안 함.
  · 비고      : callOpenAI 경로는 폴백/참고로 유지.

[3-4] 수집-분석 "동기 결합" 방식 (초기 → 분리)
  · 썼던 이유 : 구현이 단순(수집 끝나면 바로 분석).
  · 버린 이유 : 수집이 LLM 속도/한도에 묶여 같이 느려지고 실패함(최대 5분 대기).
  · 대체      : producer/consumer 분리(수집=적재만, 분석=별도 잡). (4장·5장 참조)

[3-5] 단일/짧은 글자 섹터 "부분일치" 매칭 (초기 → 문맥매칭/제외)
  · 썼던 이유 : 구현이 쉬움(text.contains("금") 등).
  · 버린 이유 : "금"이 금융/현금/세금/골드만삭스에, "은"이 은행/은퇴/받은…에 매칭 →
                거짓 양성 폭증(은 9,446건). 한국어 음절·조사 특성상 불가피.
  · 대체      : 금/은은 본문 추출 제외 + LLM 의미판단으로만, 조선/사료/통신/기계는
                "문맥 표현"이 있을 때만 인정.

[3-6] generateMockAnalysis (목업 분석) — 폴백으로만 유지
  · 썼던 이유 : API 키 없을 때 로컬 테스트용 가짜 분석.
  · 문제      : 키를 dummy로 두면 모든 그룹이 목업으로 처리돼 4종목만 매핑되는 등
                데이터 오염. → 실제 LLM(Groq) 연결로 해결. 목업은 최후 폴백으로만.

[3-7] Jsoup 보조 수집기 — 기본 비활성
  · 왜 안 쓰나 : 사이트 직접 크롤링은 약관 리스크. 네이버 공식 API로 충분.



════════════════════════════════════════════════════════════════════════════
 4. 사용한 핵심 기법(개념) — 무슨 개념이고 왜 썼나
════════════════════════════════════════════════════════════════════════════

[4-1] content_hash 기반 완전중복 제거
  · 개념 : 제목+언론사로 해시를 만들어 동일 기사를 빠르게 걸러냄.
  · 이유 : 같은 기사가 여러 번 들어와 DB가 부푸는 것을 방지. 중복은 저장 대신
           그룹의 duplicate_count만 +1.

[4-2] 유사도 그룹화 (Jaccard 유사도)
  · 개념 : 두 제목의 "단어 집합"이 얼마나 겹치는지 = (교집합/합집합)로 0~1 점수.
           임계값 이상이면 같은 이슈로 보고 한 그룹에 묶음.
  · 이유 : 같은 사건을 다룬 여러 기사를 "1개 이슈"로 압축 → 분석 대상 수를 줄임.
  · 비고 : 2차 고도화 후보 = TF-IDF Cosine / 임베딩 벡터 유사도.

[4-3] 대표 1건 분석 + 그룹 전파 (LLM 비용 절감의 핵심)
  · 개념 : 그룹에서 가장 최신/대표 기사 1건만 LLM에 보내고, 결과(호재/악재 등)를
           그룹 내 모든 기사·종목·섹터 매핑에 전파.
  · 이유 : LLM 호출 = 돈/한도. N건을 1건으로 줄이는 가장 강력한 절감.

[4-4] producer/consumer 분리 (DB를 작업 큐로 사용)
  · 개념 : "생산자(수집)"는 DB에 적재만, "소비자(분석)"는 미분석 표시(analyzed_yn='N')를
           큐처럼 꺼내 처리. 둘을 별도 스레드/스케줄로 분리.
  · 이유 : 수집이 LLM 속도에 안 막히게. 분석은 자기 예산(한도) 안에서 천천히 소화.

[4-5] 배치 LLM 호출 (Batching)
  · 개념 : 여러 그룹을 한 프롬프트의 JSON 배열로 묶어 한 번에 분석, 결과 배열을 분해.
  · 이유 : 호출 수를 1/N로 줄여 무료 RPD/RPM을 절약. (특히 Gemini 20회/일에 유효)

[4-6] 노출도 컷 (duplicate_count 임계값)
  · 개념 : 여러 매체가 보도(중복 많은)한 그룹만 분석. 1개 매체만 보도한 자잘한 뉴스는 제외.
  · 이유 : 한정된 분석 예산을 "중요한(많이 다뤄진) 뉴스"에 집중.

[4-7] 캐시 + 실패 시 마지막 정상값 폴백 (KIS 시세)
  · 개념 : 종목 시세를 짧게(12초) 캐시. 외부 호출 실패 시 0이 아니라 "직전 정상값"을 반환.
  · 이유 : 거래량/시총이 갱신마다 0↔정상으로 깜빡이는 현상 제거.

[4-8] 스로틀링(Throttle) / Rate limiting
  · 개념 : 외부 API 호출 사이 최소 간격을 강제(전역 락 + 마지막 호출시각).
  · 이유 : KIS "초당 호출 초과(EGW00201)", Groq RPM 등 한도를 코드 레벨에서 준수.

[4-9] 이중검사 락 (Double-Checked Locking) — 토큰 동시발급 방지
  · 개념 : "토큰 있나?"를 락 밖에서 한 번, 락 안에서 또 한 번 확인. 한 스레드만 발급.
  · 이유 : 22개 요청이 동시에 토큰을 발급하려다 EGW00133(1분당 1회) 폭주하던 버그 해결.

[4-10] 토큰 디스크 영속화
  · 개념 : 발급한 KIS 토큰(만료시각 포함)을 파일에 저장 → 재기동 시 재발급 없이 재사용.
  · 이유 : 토큰은 ~24시간 유효한데 재기동마다 재발급하면 한도(1분당 1회)에 걸림.

[4-11] 문맥 기반 키워드 매칭 (거짓 양성 제거)
  · 개념 : 짧고 흔한 단어(금/은/조선/사료/통신/기계)는 단순 포함 대신, "상품/시세/업종
           문맥 표현"이 있을 때만 섹터로 인정. 금/은은 아예 본문추출 제외하고 LLM 판단만.
  · 이유 : "받고 싶은 선물"이 "은 선물(silver futures)"로, "골드만삭스"가 "금"으로 잡히는
           한국어 부분일치 거짓양성 차단.

[4-12] 화이트리스트 가드
  · 개념 : 허용된 섹터/거시명만 생성/매핑(예: 코스피/코스닥/나스닥만 지수로 인정).
  · 이유 : LLM/추출이 만들어내는 쓰레기 섹터("코스피, 치매 관련 연구…" 등) 방지.

[4-13] duplicate_count 가중 집계 (버즈량)
  · 개념 : 대시보드의 섹터/종목 호재·중립·악재 "숫자"는 그룹 수가 아니라
           Σ duplicate_count(중복 보도 가중 합). "얼마나 많이 회자되나"를 표현.
  · 주의 : 고유 뉴스 건수와 다름(예: 바이오 중립 10,866 = 1,358개 뉴스의 중복 합).

[4-14] 보안 기법 (계획서 9장)
  · PreparedStatement : 모든 SQL을 파라미터 바인딩 → SQL Injection 방지.
  · CSRF 토큰         : 상태변경(POST=분석실행 버튼)에 세션 토큰 검증(CsrfFilter).
  · XSS 방지          : JSP는 c:out/escape, JS는 textContent 사용.
  · 키 비노출         : API 키는 환경변수로만, 로그/프론트/예외에 노출 금지.

 5. 단계별 구현 상세 (수집 → 분석/요약 → 표출 → 인프라)

────────────────────────────────────────────────────────────────────────────
 5.1 수집(Collect) — "뉴스를 모아 DB에 정리해 적재"
────────────────────────────────────────────────────────────────────────────
· 관련 클래스
  - NaverNewsApiCollector : 네이버 검색 API 호출(서버사이드), JSON→NewsArticleDTO.
  - CollectJob            : 수집 1회 실행 단위(스케줄러/버튼 공용). 적재까지만 담당.
  - QuotaGuard            : 일일 호출 한도(25,000) 가드 + 동적 수집주기 산정.
  - NewsCollectScheduler  : 데몬 스레드 기반 주기 실행기.
  - NewsCollectContextListener : 앱 시작/종료 시 스케줄러 가동/안전종료.
  - SettingsService       : collect_settings(키워드/주기/한도 등)를 DB에서 읽음.
  - ArticleService        : 저장 + 중복제거 + 유사도 그룹화 파이프라인.
  - SimilarityService     : content_hash, 정규화, Jaccard 유사도, 그룹 매칭.

· 동작 원리(순서)
  1) 키워드 선정 : SettingsService.getKeywords()
       = collect.keywords(증시/경제/정책/과학·기술/산업 키워드) + stock_master 전체 종목명.
       CollectJob은 1회에 collect.max.per.run(기본 100)개씩 회전(rotate) 처리.
  2) 한도 체크   : QuotaGuard.canCall() — 오늘 호출수 + 요청수 ≤ 25,000*0.8 인지.
  3) 호출        : NaverNewsApiCollector.collect(키워드, 30) → 기사 30건 DTO.
  4) 섹터 태깅   : 키워드가 허용 섹터면 그대로, 아니면 본문에서 섹터 추출
                   (ArticleService.extractSectorsFromText — 문맥매칭 적용).
  5) 적재/그룹화 : ArticleService.saveAll()
       - content_hash로 완전중복 검사(중복이면 그룹 카운트만 +1)
       - 신규면 insert 후, 최근 24시간 활성 그룹들과 Jaccard 유사 매칭
       - 매칭되면 그룹에 합류(대표가 더 최신이면 대표 교체), 아니면 새 그룹 생성
       - 그룹-섹터 매핑(news_sector_map), 요약 갱신(GroupSummaryService)
  6) 다음 인덱스 저장 : collect.last.index 갱신(다음 회전 위치).

· 사용 기법/도구
  - 스케줄러 안전설계 : ScheduledThreadPoolExecutor + setRemoveOnCancelPolicy(true)
       + daemon 스레드 + scheduleWithFixedDelay + 종료 시 shutdown→awaitTermination→
       shutdownNow. (Tomcat 메모리 누수·종료 차단 함정 회피)
  - 동적 주기 : QuotaGuard.dynamicIntervalSec(키워드수). 단, 회전 처리 모델에선
       collect.interval.sec(현재 10분=600초)로 오버라이드해 합리화.
  - 요약 스레드 풀 : 그룹 요약 갱신을 그룹마다 new Thread로 띄우던 것을 →
       공유 데몬 고정풀(SUMMARY_POOL, core2/max3, CallerRunsPolicy)로 제한(스레드 폭증 방지).

· 현재 운영 : 자동 수집(collect.auto.enabled=Y), 주기 10분. 분석은 분리(아래).


────────────────────────────────────────────────────────────────────────────
 5.2 분석·요약(Analyze / Summarize) — "적재된 뉴스를 AI로 판정·요약"
────────────────────────────────────────────────────────────────────────────
· 관련 클래스
  - AnalyzeJob       : 분석 1회 실행 단위(버튼/스케줄). 자체 isRunning 가드.
  - AnalyzeService   : 미분석 그룹 조회 → 배치 LLM 호출 → 저장/전파.
  - callGroqBatch / callOllamaBatch / callGeminiBatch : 제공자별 LLM 호출.
  - parseBatchResults : LLM 응답(JSON 배열/{results:[]}/단일객체) 견고 파싱 + 점수 clamp.
  - StockResolver    : 분석 텍스트에서 stock_master 종목명/코드 매칭(2,700+).
  - GroupSummaryService : 외부 AI 없이 규칙기반 추출 요약(보조).

· 동작 원리(순서)
  1) 대상 선정 : fetchUnanalyzedGroups()
       WHERE analyzed_yn='N'
         AND duplicate_count >= analyze.min.duplicate.count(기본 2)   ← 노출도 컷
         AND last_collected_at >= 오늘-1일                            ← 최근 2일(어제+오늘)
       ORDER BY duplicate_count DESC, last_collected_at DESC          ← 중요/최신 우선
       LIMIT analyze.max.per.run(기본 200)
  2) 제공자 선택 : analyze.provider = groq | ollama | gemini (현재 groq).
  3) 배치 호출 : 그룹 N개(groq batch 3 등)를 한 프롬프트의 JSON으로 묶어 호출.
       - 프롬프트가 "JSON만, 한국어로, 허용 섹터만, 스키마 준수"를 강제.
       - 응답을 parseBatchResults로 id 매핑, impact_score(-5~5)/confidence(0~100) clamp.
  4) 저장/전파 : saveAnalysisResult()
       - news_ai_analysis 에 요약/판정/영향도/리스크 저장
       - 그룹(news_similarity_group) good_bad_type/impact_score/group_summary 갱신 +
         analyzed_yn='Y'
       - 섹터 매핑(허용 섹터만), 종목 매핑(LLM 지목 + StockResolver 이름매칭),
         거시(코스피/환율/유가/금/은…) 매핑(콤마 분리·쓰레기 이름 차단)
  5) 한도 처리 : 429를 "일일(RPD) 소진=실행중단" vs "분당(RPM/TPM)=백오프 후 재시도"로
       구분. 무한 재시도(livelock) 방지를 위해 재시도 상한.

· 요약(Summarize)은 두 갈래
  - LLM 요약  : summary_short / summary_detail (AI가 생성).
  - 룰베이스  : GroupSummaryService — 그룹 내 description에서 핵심 문장 추출(외부 AI 불필요).
                LLM 비용을 줄이고 싶을 때 요약을 이쪽으로 분리 가능.

· 사용 기법/도구
  - 배치 호출(4-5), 노출도 컷(4-6), 제공자 추상화(groq/ollama/gemini 한 줄 전환),
    JSON 강제 + 견고 파싱, 점수 clamp, 종목 이름매칭(StockResolver).
  - Groq 특이점 : OpenAI 호환 /chat/completions + response_format=json_object.
    Cloudflare 차단 회피 위해 User-Agent: Mozilla/5.0 헤더 필수.

· 현재 운영 : 분석 자동 OFF(analyze.auto.enabled=N). 대시보드의
  "분석·요약 실행" 버튼(POST /collect/run → AnalyzeJob)을 누르면, 적재된 미분석
  뉴스를 Groq로 분석. (수집은 자동 10분, 분석은 사용자 트리거)


────────────────────────────────────────────────────────────────────────────
 5.3 표출(Display) — "분석 결과를 대시보드로 보여주기"
────────────────────────────────────────────────────────────────────────────
· 관련 클래스/파일
  - DashboardServlet (/api/dashboard) : 집계 JSON 산출(조회 전용).
  - StockInfoServlet (/api/stock/info) : 종목 실시간 시세(KIS)+재무(DART).
  - KisApiClient : KIS 토큰 관리 + 시세 호출 + 캐시/throttle/토큰영속화.
  - dashboard.jsp / dashboard.js : 화면 + 비동기 렌더링.
  - CollectRunServlet / CollectStatusServlet : 분석 버튼 트리거 + 상태 폴링.

· 동작 원리
  - 대시보드 데이터(/api/dashboard) : 모두 PreparedStatement 집계.
      · summary       : 호재/악재/중립 그룹 수.
      · topIssues     : 호재2+악재2+중립2 = 영향도 강한 순 상위 6개.
      · sectors       : 섹터별 Σ duplicate_count 가중(호재/중립/악재) + 평균 영향도.
      · macroSignals  : 지수/거시(코스피/환율/유가/금/은…) 신호.
      · stockSignals  : 종목별 신호 상위 15.
      · 공통 필터     : analyzed_yn='Y' AND 최근 3일(last_collected_at).
      · 주요 이슈 태그 : 그룹의 related_sectors(정리된 매핑에서 재생성).
  - 실시간 시세(/api/stock/info) : KisApiClient
      · 종목별 12초 캐시 + 실패 시 마지막 정상값(0 깜빡임 방지)
      · 전역 throttle(초당 한도 준수) + 토큰 디스크 영속화(EGW00133 회피)
      · KIS 실패 시 네이버 시세로 폴백(거래량/시총은 없어 생략→프론트가 직전 값 유지)
  - 프론트(dashboard.js) : vanilla JS fetch. 종목표는 250ms 큐로 호출 분산,
      매크로/시세는 15초 주기 갱신. 표시값이 0/빈값이면 갱신 스킵(직전 값 유지).
  - 버튼 흐름 : "분석·요약 실행" → CSRF 토큰 헤더로 POST /collect/run →
      AnalyzeJob 시작 → /api/collect/status 폴링(AnalyzeJob.isRunning) → 끝나면 화면 갱신.

· 사용 기법/도구
  - duplicate_count 가중 집계(버즈량), 3일 윈도우, 화이트리스트 섹터,
    KIS 캐시/throttle/토큰영속화, CSRF, XSS escape.

 5.4 인프라(Infra) — "구동/배포/운영 환경"
────────────────────────────────────────────────────────────────────────────
· 구성
  - 런타임 : JDK8 + Tomcat 8.5 (WAR: newssignal.war → 컨텍스트 /newssignal2).
  - DB     : MariaDB 10.1 (utf8mb4), HikariCP 풀.
  - LLM    : Groq(클라우드) 기본 / Ollama(로컬, 선택) / Gemini(선택).
  - 번들   : env/ 폴더에 JDK·Tomcat·Maven·MariaDB를 함께 둠(무설치 구동). 단 Git 제외.

· 기동(start.ps1) 순서
  1) 환경변수(키/DB/LLM) 설정
  2) MariaDB 3306 확인 → 없으면 mysqld 자동기동(없으면 HikariCP 실패=404 방지)
  3) Ollama 11434 확인 → (provider=ollama일 때) 자동기동
  4) Maven clean package → target/newssignal.war
  5) WAR을 Tomcat webapps/newssignal2.war 로 복사(핫 배포)
  6) catalina run 으로 Tomcat 기동

· 운영상 알게 된 것(중요)
  - 형제 프로젝트 /newssignal(구버전)과 같은 Tomcat·DB·KIS계정을 공유 →
    · KIS 토큰/한도를 두 앱이 경쟁(구버전이 선점해 EGW00133 유발)
    · 구버전 재배포가 collect_settings를 리셋(수집 OFF/섹터 재오염)
    → 형제 앱을 "되돌릴 수 있게 비활성화"(war→.disabled) 권장.
  - 대시보드가 빈 화면 = 데이터가 "최근 3일" 윈도우 밖. 서버가 며칠 꺼져 있으면
    수집이 멈춰 데이터가 오래됨 → 재기동+수집+분석으로 채워짐.

· 보안/형상관리
  - 키는 환경변수(start.ps1). start.ps1은 .gitignore(키 보호) + start.ps1.example 템플릿.
  - env/(수 GB), 임시 산출물(temp_*, dash*.json 등)은 .gitignore.
  - GitHub(zzawoo/NewsSignal_stock2)에 코드/문서/SQL만 푸시.

  - 거래량/거래대금/시총이 갱신마다 0↔정상.
  - 원인: KIS rate limit(EGW00201)+토큰 동시발급(EGW00133), 실패 시 네이버 폴백이 0으로.
  → 시세 캐시(12초)+마지막 정상값, throttle, 토큰 이중검사 락+디스크 영속화,
    프론트 방어적 갱신.

[문제 3] 수집/분석 결합 → 분리
  - 수집이 LLM에 묶여 지연/실패.
  → CollectJob(적재만) + AnalyzeJob(분석) 분리. dup컷+최근2일+배치로 처리량↑.

[문제 4] LLM 엔진 여정
  - Gemini 무료 RPD 20/일 한계 → Ollama 로컬(무료·무제한, 그러나 CPU라 1건 72초) →
    Groq 클라우드(무료·빠름 1건 2.4초)로 정착. (Cloudflare UA 함정 해결, 점수 clamp)

[문제 5] 섹터 거짓 양성
  - 은 9,446 / 금 3,822 등 비정상(은행/현금/골드만삭스/실버타운 오매칭).
  → 금/은 본문추출 제외+LLM 의미판단, 조선/사료/통신/기계 문맥매칭,
    related_sectors 재생성, 거시 섹터 콤마분리·쓰레기 차단.

[현재]
  - 수집: 자동 10분(증시/경제/정책/과학+상장종목).
  - 분석/요약: "분석·요약 실행" 버튼 → Groq 배치.
  - 표출: 대시보드(주요 이슈/연관 섹터 버즈량/종목 신호/실시간 시세, 최근 3일).
  - 인프라: start.ps1 원클릭(MariaDB/Ollama 자동기동), 토큰 영속화, GitHub 연동.

 7. 향후 개선 제안
